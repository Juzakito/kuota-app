# Kuota demo backend

This is a **local demo service only**. By default it binds to `127.0.0.1`, uses one synthetic buyer and one synthetic supplier, signs supplier QRs with a local secret, and persists only synthetic quotes and demo purchase records to `backend/data/kuota-demo-store.json`. It also applies in-process fixed-window rate limits to public and authenticated routes; those limits reset on restart and are not shared between instances. For a phone test on the same trusted Wi-Fi, set `HOST` to the PC's private Wi-Fi IP; do not expose the service to the public internet.

It does not perform identity verification, scoring, lending, supplier settlement or payment processing by default. Identity returns `501 NOT_CONFIGURED`. The default payment routes are a deterministic local simulator: they create no charge, transfer, refund or real debt. A demo purchase is labeled `DEMO_CREATED` and must never be treated as a real sale, receivable or debt.

`KUOTA_ENVIRONMENT=production` is a fail-fast preparation mode, not an enabled production deployment. It requires Mercado Pago Checkout Pro, PostgreSQL and 32+ character secrets or the server refuses to start. This repository contains no merchant credentials, has not received real money and still needs legal, commercial, security and reconciliation approval before use with clients.

## Run locally on Windows

From the Kuota App project folder, use Android Studio's Terminal or PowerShell:

```powershell
$env:JAVA_HOME = 'C:\Users\josem\AppData\Local\Programs\Eclipse Adoptium\jdk-17.0.20.101-hotspot'
.\gradlew.bat -p backend run
```

By default the server listens on `http://127.0.0.1:8080`. Health check: `GET http://127.0.0.1:8080/health`.

The Android debug build defaults to the emulator host alias `10.0.2.2`. Start the server, sync Gradle and run the app in an Android emulator. To override the base URL, put this in the user's Gradle properties file (`%USERPROFILE%\.gradle\gradle.properties`) and sync/rebuild:

```properties
KUOTA_API_BASE_URL=http://10.0.2.2:8080/
```

For a phone connected to the same Wi-Fi, bind the backend to the PC's private Wi-Fi address and build the debug APK with that same address. Example only; replace the IP with the PC's current Wi-Fi IPv4 address:

```powershell
$env:HOST = '192.168.1.20'
.\gradlew.bat -p backend run
.\gradlew.bat -PKUOTA_API_BASE_URL=http://192.168.1.20:8080/ :app:copyDebugApkForSharing
```

If Windows Firewall blocks the connection, allow the demo server only on the trusted private Wi-Fi network. This HTTP configuration is debug-only; release builds still require HTTPS.

For a phone connected by USB, keep the server on `127.0.0.1` and forward the port instead of fighting the firewall:

```powershell
adb reverse tcp:8080 tcp:8080
```

Then build with `-PKUOTA_API_BASE_URL=http://127.0.0.1:8080/`, or change the server URL inside the app under **Notificaciones → Avanzado**.

Cleartext HTTP is permitted only by the Android debug manifest and only for the emulator alias or a private IPv4 address in the API factory. Release builds reject HTTP. The financing screen can request a short-lived demo QR or paste one generated by `/supplier-portal`, asks the backend to verify its signature and expiry, then requests demo eligibility and a quote against that signed payload. The screen shows no supplier amount or installment plan until the server verifies the QR, and its demo supplier confirmation calls the backend instead of calculating amounts locally. Identity and real payment providers remain disabled.

Purchase demo safety behavior:

- Repeating the same purchase request with the same `Idempotency-Key` returns the original demo purchase.
- Reusing that key for a different request returns `409 IDEMPOTENCY_KEY_REUSED`.
- A quote can create only one demo purchase; another key for that quote returns `409 QUOTE_ALREADY_USED`.
- The request must use `DEMO_ONLY_NOT_ACCEPTED` for the terms and privacy fields. The service does not store legal acceptance.
- After supplier confirmation, the Android app links the demo account if needed and registers the purchase with `POST /v1/purchases`. Actividad then reads `GET /v1/purchases` and shows the `DEMO_CREATED` record, its installment schedule and the warning that it is not a sale, debt or disbursement.

## Signed supplier QR (demo)

Supplier QRs are HMAC-SHA256-signed Base64 JSON payloads. The Android app no longer contains the signing secret and does not verify signatures locally; it calls the backend.

| Route | Auth | Limit | Behavior |
|---|---|---|---|
| `POST /v1/supplier/qr/verify` | Public | 30/min per client IP | Verifies signature, required fields, positive amount and expiry. Returns `transaction_id`, `supplier_id`, `supplier_name`, `amount_cents` and expiry, or `422 QR_INVALID_OR_EXPIRED`. |
| `POST /v1/supplier/generate-qr` | Public, demo only | 10/min per client IP | Form field `amountPen` (default `1000`). Returns a signed payload valid for 15 minutes under the synthetic supplier. Production returns `403 SUPPLIER_DEMO_ONLY`. |
| `POST /v1/supplier/confirm-sale` | Public, demo only | 20/min per client IP | Body `{"qr_payload":"..."}`. Re-verifies the QR and derives the 60% immediate payout, 40% deferred payout and 4% supplier fee from its signed amount. Returns `DEMO_SUPPLIER_CONFIRMED`, never a real settlement. Production returns `403 SUPPLIER_DEMO_ONLY`. |

- `KUOTA_QR_SIGNING_SECRET` (32+ characters) signs the payloads. Demo generates an ephemeral secret with a warning when absent; a restart invalidates previously generated QRs. Production refuses to start without it.
- `POST /v1/quotes` verifies the signed payload before creating a quote and rejects an amount that differs from the signed amount with `QR_AMOUNT_MISMATCH`. The legacy plain-text `KUOTA-DEMO-SUPPLIER-LIMA` payload is accepted only outside production for backward compatibility.
- Payload size is capped at 4,096 characters. Signatures are compared with `MessageDigest.isEqual`.
- `/supplier-portal` shows a sample signed QR for manual demos.

## Authentication and ownership

`KUOTA_JWT_SECRET` (32+ characters) signs the HS256 access tokens issued by `POST /v1/auth/verify-otp`. Tokens expire after 24 hours, carry `iss=kuota-peru-auth`, and verification pins `alg=HS256` with a constant-time signature comparison. In demo mode the server generates an ephemeral secret when the variable is absent and logs a warning; restarting invalidates every token. Production refuses to start without `KUOTA_JWT_SECRET`.

The OTP flow is simulated: `request-otp` returns the demo code `123456` in its response and `verify-otp` accepts only that exact code. In production both routes return `503 OTP_PROVIDER_NOT_CONFIGURED`. Demo limits are 10 requests and 20 verifications per IP per 10 minutes, plus 3 requests and 5 verifications per phone number per 10 minutes. This is not real authentication: there is no SMS delivery, attempt counter, refresh token or revocation.

Routes requiring `Authorization: Bearer <token>`:

- `GET /v1/me`
- `POST /v1/purchases`, `GET /v1/purchases`, `GET /v1/purchases/{purchaseId}`, `GET /v1/purchases/{purchaseId}/installments`
- `POST /v1/installments/{installmentId}/payment-intents`
- `GET /v1/payments/{paymentId}`, `POST /v1/payments/{paymentId}/demo-events`

Purchases belong to the authenticated user. History is filtered, and another user's purchase, installment, payment, or idempotency key behaves like a missing resource (`404`, or `409` for idempotency reuse) without revealing whether it exists. `GET /v1/demo/reconciliation` accepts only the ledger admin token (`X-Kuota-Admin-Token` or `Bearer <KUOTA_ADMIN_TOKEN>`).

Demo records created before ownership existed have no owner and are no longer visible through HTTP. Delete `backend/data/kuota-demo-store.json` (and the ledger files for a clean slate) to reset the demo data.

## Request correlation and error contract

Every response includes `X-Request-Id`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`. An inbound `X-Request-Id` is reused only when it matches `^[A-Za-z0-9._:-]{1,64}$`; otherwise the server generates a UUID.

Error bodies have a stable shape:

```json
{ "code": "QR_INVALID_OR_EXPIRED", "message": "…", "request_id": "…", "retryable": false }
```

`retryable` is always serialized, including when `false`. A `429 RATE_LIMITED` response is retryable and includes `Retry-After`. Unexpected failures return `500 INTERNAL_ERROR` with `retryable=true` and the same request id, without exposing stack traces or provider text. The Android app shows the request id as a support reference.

## Payment provider: demo simulator or Mercado Pago

The Android app still sends `DEMO_MANUAL`; no mobile screen opens a real checkout yet. The backend boundary lets a deployment switch providers through environment variables.

| Variable | Meaning |
|---|---|
| `KUOTA_ENVIRONMENT` | `demo` (default) or `production`. Production fails fast unless every requirement below is present. |
| `KUOTA_PAYMENT_PROVIDER` | `demo` (default) or `mercadopago`. |
| `KUOTA_MP_ACCESS_TOKEN` | Mercado Pago merchant access token. Never commit it. |
| `KUOTA_MP_WEBHOOK_SECRET` | Secret configured in the Mercado Pago webhook panel. |
| `KUOTA_MP_NOTIFICATION_URL` | Public HTTPS URL of `/v1/webhooks/mercadopago`. Alternatively set `KUOTA_PUBLIC_BASE_URL`. |
| `KUOTA_MP_BACK_URL` | Optional return URL for Checkout Pro. |
| `KUOTA_MP_API_BASE_URL` | Optional API override; defaults to `https://api.mercadopago.com`. |
| `KUOTA_WEBHOOK_SECRET` | Shared secret for generic HMAC webhooks (32+ characters in production). |
| `KUOTA_ADMIN_TOKEN` | Token for ledger inspection and the demo reconciliation queue (32+ characters in production). |
| `KUOTA_JWT_SECRET` | HS256 secret for access tokens (32+ characters). Required in production; demo generates an ephemeral one when absent. |
| `KUOTA_QR_SIGNING_SECRET` | HMAC-SHA256 secret for signed supplier QRs (32+ characters). Required in production; demo generates an ephemeral one when absent. |
| `KUOTA_DATABASE_URL` | PostgreSQL JDBC URL, with or without the `jdbc:` prefix. Required whenever Mercado Pago is enabled and in production. |
| `KUOTA_DATABASE_USER`, `KUOTA_DATABASE_PASSWORD`, `KUOTA_DATABASE_POOL_SIZE` | Database credentials and pool size (1–20). |

Behavior when `KUOTA_PAYMENT_PROVIDER=mercadopago`:

- PostgreSQL is mandatory: a real provider cannot use the demo file ledger, even with `KUOTA_ENVIRONMENT=demo`.
- `POST /v1/installments/{installmentId}/payment-intents` requires `payment_method_id=MERCADO_PAGO_CHECKOUT` and creates a Checkout Pro preference with the installment amount, an external reference to the internal payment ID, metadata, and an idempotency key.
- The attempt is stored as `ACTION_REQUIRED` and the response includes `next_action_url` (the checkout URL). Opening that URL is the missing mobile integration.
- If preference creation fails, the attempt is marked `FAILED` with the provider code, the installment returns to `PROGRAMMED`, and no ledger entry is written.
- Webhooks never trust the state carried in the payload: the server fetches `GET /v1/payments/{id}` from Mercado Pago and settles only with that authoritative status, amount, currency and external reference.
- An approved checkout does not create debt by itself. Only an approved payment whose amount and currency match the installment produces `CASH`/`BUYER_RECEIVABLE` ledger entries.

## Signed webhooks and deduplication

Both endpoints cap the body at 64,000 characters, reject oversized payloads with `413`, and never log the raw payload.

### Mercado Pago

`POST /v1/webhooks/mercadopago` is enabled only when `KUOTA_MP_WEBHOOK_SECRET` exists. It verifies the `x-signature` and `x-request-id` headers against `data.id` from the query string:

```text
manifest = "id:<data.id>;request-id:<x-request-id>;ts:<ts>;"
expected = lowercase_hex(HMAC-SHA256(KUOTA_MP_WEBHOOK_SECRET, manifest))
x-signature: ts=<ts>,v1=<expected>
```

- The `request-id:` segment is included only when the header is present.
- Timestamps older or newer than 300 seconds are rejected.
- A missing or invalid signature returns `401 WEBHOOK_SIGNATURE_INVALID`.
- `data.id` in the query string must match the body; a mismatch returns `400 WEBHOOK_DATA_ID_MISMATCH`.
- Notifications whose topic is not `payment` return `200 IGNORED`.
- Deduplication uses the Mercado Pago event ID (`payload.id`, or a SHA-256 of the body as fallback) in the `webhook_event` table / NDJSON inbox. Completed or ignored events return `200 DUPLICATE`; an event already in progress returns `409`.
- A lookup failure returns `502` and leaves the event retryable, so Mercado Pago can deliver it again.

### Generic HMAC

`POST /v1/webhooks/hmac` is enabled only when `KUOTA_WEBHOOK_SECRET` exists:

```text
X-Kuota-Timestamp: <unix-seconds>
X-Kuota-Signature: v1=<lowercase_hex(HMAC-SHA256(secret, "<timestamp>.<raw-body>"))>
```

The 300-second tolerance, constant-time comparison, provider/event validation and deduplication are identical to the Mercado Pago flow. The normalized body is:

```json
{
  "event_id": "evt-100",
  "provider": "demo",
  "payment_id": "<internal payment id>",
  "provider_payment_id": "psp-9",
  "status": "APPROVED",
  "amount_cents": 18750,
  "currency": "PEN",
  "occurred_at": "2026-10-20T12:00:00Z"
}
```

Supported statuses: `APPROVED`/`SUCCEEDED`/`PAID`, `PENDING`, `PROCESSING`/`IN_PROCESS`, `REJECTED`/`FAILED`/`CANCELLED`, `REFUNDED`, and `REVERSED`/`CHARGED_BACK`.

## Append-only accounting ledger

With `KUOTA_DATABASE_URL` the backend uses PostgreSQL and Flyway migration `V1__append_only_ledger.sql`. Without a database it uses an append-only NDJSON file (`data/kuota-ledger.ndjson`) plus a webhook inbox (`data/kuota-webhook-events.ndjson`); both are for demo only and flush with `fsync`.

PostgreSQL enforcement:

- `ledger_transaction` and `ledger_posting` only accept `INSERT`; triggers reject `UPDATE`, `DELETE` and `TRUNCATE`.
- A deferred constraint trigger checks at commit that total debits equal total credits and that the transaction has postings.
- `(environment, kind, source_type, source_id)` is unique, so retries cannot duplicate financial history.
- `DEMO` and `PRODUCTION` entries are stored in the same tables but reported separately.

Chart of accounts: `CASH`, `BUYER_RECEIVABLE`, `SUPPLIER_PAYABLE_IMMEDIATE`, `SUPPLIER_PAYABLE_DEFERRED`, `REVENUE_BUYER_FEE`, `REVENUE_SUPPLIER_FEE`, `PAYMENT_VARIANCE`.

Example for a S/ 1,000 purchase (100,000 céntimos, 30% down payment, 5% buyer fee, 60/40 supplier split, 4% supplier fee):

```text
PURCHASE_RECOGNITION
  DEBIT   BUYER_RECEIVABLE              105,000
  CREDIT  SUPPLIER_PAYABLE_IMMEDIATE     60,000
  CREDIT  SUPPLIER_PAYABLE_DEFERRED      36,000
  CREDIT  REVENUE_BUYER_FEE               5,000
  CREDIT  REVENUE_SUPPLIER_FEE            4,000

INSTALLMENT_PAYMENT (matched, 18,750)
  DEBIT   CASH                           18,750
  CREDIT  BUYER_RECEIVABLE               18,750

INSTALLMENT_REFUND / INSTALLMENT_CHARGEBACK
  DEBIT   BUYER_RECEIVABLE               18,750
  CREDIT  CASH                           18,750

INSTALLMENT_RECONCILIATION (provider paid 18,751)
  DEBIT   CASH                           18,751
  CREDIT  BUYER_RECEIVABLE               18,750
  CREDIT  PAYMENT_VARIANCE                    1
```

The down payment is part of `BUYER_RECEIVABLE`; the ledger does not invent cash for it until a real payment event arrives. Commissions are recorded as revenue, not subtracted from the supplier's gross split beyond the documented 4% fee.

Start PostgreSQL locally:

```powershell
docker compose -f backend/docker-compose.yml up -d
$env:KUOTA_DATABASE_URL = 'postgresql://127.0.0.1:5433/kuota'
$env:KUOTA_DATABASE_USER = 'kuota'
$env:KUOTA_DATABASE_PASSWORD = 'kuota_demo_password'
$env:KUOTA_ADMIN_TOKEN = '<at least 32 characters>'
.\gradlew.bat -p backend run
```

Inspect the ledger (the token is optional in demo, required in production):

```powershell
curl -H "X-Kuota-Admin-Token: $env:KUOTA_ADMIN_TOKEN" http://127.0.0.1:8080/v1/admin/ledger/balances
curl -H "X-Kuota-Admin-Token: $env:KUOTA_ADMIN_TOKEN" "http://127.0.0.1:8080/v1/admin/ledger/transactions?limit=50"
```

`balances` includes `balanced: true` when the net sum of all accounts is zero. Without `KUOTA_ADMIN_TOKEN` both routes return `503 LEDGER_ADMIN_DISABLED`; an invalid token returns `401`.

## Simulated payments and reconciliation

The demo routes below are available only while `KUOTA_PAYMENT_PROVIDER=demo`; `demo-events` returns `403 DEMO_EVENTS_DISABLED` when a real provider or production environment is configured. They do not contact a bank, PSP, Yape, Plin or customer payment method.

- Create an intent with `POST /v1/installments/{installmentId}/payment-intents`, `Idempotency-Key: <unique-key>`, and JSON `{"payment_method_id":"DEMO_MANUAL"}`. A new attempt starts as `PENDING`.
- Read the durable status and event history with `GET /v1/payments/{paymentId}`. The purchase-history response includes its payment attempts.
- Simulate state transitions with `POST /v1/payments/{paymentId}/demo-events`, an idempotency key, and JSON `{"event_type":"PROCESSING"}`. Allowed events: `PROCESSING`, `SUCCEED`, `FAIL`, `SUCCEED_AMOUNT_MISMATCH`, `SUCCEED_REFERENCE_MISMATCH`, `REVERSE`, `REFUND`, `RECONCILE_MATCH`.
- `SUCCEED` creates a synthetic reference and matching amount. Mismatch events produce a synthetic settlement that remains in the reconciliation queue; `RECONCILE_MATCH` records explicit manual resolution without overwriting the original synthetic provider reference or amount.
- See unresolved synthetic settlements at `GET /v1/demo/reconciliation`, authenticated with the ledger admin token. Reversal and refund are separate, audited events; failed attempts can be retried with a new idempotency key.
- Repeating the same event with the same key and body returns the current payment record; reusing the key with different content returns `409 IDEMPOTENCY_KEY_REUSED`. Invalid state transitions return `409 PAYMENT_TRANSITION_INVALID`.
- Installment statuses such as `PAYMENT_PENDING`, `DEMO_PAID`, `DEMO_PAYMENT_REVIEW`, `DEMO_REVERSED` and `DEMO_REFUNDED` are explicitly synthetic.

## Remote reminders and push modes

The backend schedules demo installment reminders and supports three delivery modes:

- `FCM`: requires `KUOTA_FCM_PROJECT_ID` and `KUOTA_FCM_SERVICE_ACCOUNT` (path to the service-account JSON). The server sends data-only messages through FCM HTTP v1.
- `PULL`: used automatically for tokens starting with `pull-` (or when FCM is not configured). The device fetches `/v1/devices/{token}/inbox` with WorkManager every 15 minutes, on app start and after a sync. The inbox keeps at most 50 messages for 7 days.
- `DRY_RUN`: the backend only records the delivery in its outbox.

Endpoints (demo only):

- `POST /v1/devices` with `{"device_token":"<token>","platform":"ANDROID","app_version":"1.2.0"}`. Token length must be 20–4096 characters. Response includes `push_mode` and `quiet_hours`.
- `DELETE /v1/devices/{token}` unregisters the device.
- `GET /v1/devices/{token}/inbox` and `POST /v1/devices/{token}/inbox/ack` read and confirm pull messages.
- `POST /v1/devices/test-push` sends a synthetic test message to registered devices.
- `POST /v1/demo/reminders/run` forces the reminder scheduler; `GET /v1/demo/push/outbox` shows recorded deliveries.

Quiet hours default to 20:00–07:00 (`KUOTA_QUIET_HOURS_START` / `KUOTA_QUIET_HOURS_END`) in America/Lima. Overdue reminders are only emitted on business days. Both rules are `[VALIDACIÓN LEGAL]` and must be confirmed before production.

To enable real FCM in the Android app, add `app/google-services.json` from the Firebase console. Without that file the Gradle plugin is not applied, `BuildConfig.FIREBASE_CONFIGURED=false`, and the app registers a `pull-<uuid>` token. No Firebase credential is committed to this repository.

## Support claims (Libro de Reclamaciones) and CRM forwarding

- `POST /v1/support/claims` validates the hoja, assigns an official number (`LR-AAAA-NNNNNN`), computes a 15-business-day deadline using the Peru calendar (plus `KUOTA_EXTRA_HOLIDAYS`) and attempts delivery to every configured channel.
- `GET /v1/support/claims` lists the caller's claims; `GET /v1/support/claims/{claimNumber}` returns one claim. `GET /v1/demo/support/claims` lists all claims for demo inspection.
- Channel status is stored per claim (`PENDIENTE`, `ENVIADO`, `FALLIDO`, `DESACTIVADO`) and surfaced in the app.
- Without configuration only `ARCHIVO_LOCAL` is active: the hoja is written inside the demo data folder. This is not a real INDECOPI filing.
- Email forwarding (`CORREO_SOPORTE` and a copy to the consumer) activates with `KUOTA_SUPPORT_EMAIL` plus `KUOTA_SMTP_HOST`, `KUOTA_SMTP_PORT`, `KUOTA_SMTP_USER`, `KUOTA_SMTP_PASSWORD`, `KUOTA_SMTP_FROM`, `KUOTA_SMTP_STARTTLS` and `KUOTA_SMTP_SSL`.
- Zendesk activates with `KUOTA_ZENDESK_SUBDOMAIN`, `KUOTA_ZENDESK_EMAIL` and `KUOTA_ZENDESK_API_TOKEN`. Freshdesk activates with `KUOTA_FRESHDESK_DOMAIN` and `KUOTA_FRESHDESK_API_KEY`.
- `KUOTA_LEGAL_NAME`, `KUOTA_RUC` and `KUOTA_LEGAL_ADDRESS` fill the provider identification required on the claim sheet.

All support channels, phone numbers, emails and legal texts in the app are demo placeholders. A real deployment needs reviewed legal texts, a monitored inbox/CRM, and a documented response process for the 15-business-day deadline (Ley N° 29571).

## Tests

```powershell
.\gradlew.bat -p backend test
```

The suite covers configuration fail-fast rules, JWT signing/verification (tampering, expiry, `alg=none`, issuer, weak secrets), signed supplier QR round trip/tampering/expiry/oversize, rate-limit windows and retry-after values, Mercado Pago and generic HMAC signatures (valid, tampered, stale and malformed), webhook deduplication and retries, purchase/payment ownership isolation, balanced double-entry transactions, the append-only file ledger, persistence across restarts, and the complete purchase → payment → refund → reconciliation flow. Route-level tests use the Ktor test host to verify request-id propagation, the error contract, signed QR verification/tampering, exact demo OTP, quote amount mismatch, authenticated purchase history ownership and `429` responses. PostgreSQL is not required for the unit tests.

A manual PostgreSQL verification used `docker compose -f backend/docker-compose.yml up -d`, two matched installments (one demo event and one signed HMAC webhook), and confirmed balanced ledger totals plus rejected `UPDATE`, `DELETE` and unbalanced commits. This still does not validate a real Mercado Pago merchant account, real settlement reports or production operations.
